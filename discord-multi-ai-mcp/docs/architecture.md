# Discord マルチAI MCPサーバー アーキテクチャ（Cloudflare版）

2026年11月8日 · @ken

> この文書は実装の元になった設計文書です。実装で変えた点とその理由は [README の「設計文書からの変更点と理由」](../README.md#設計文書からの変更点と理由) にまとめています。

## 目的とスコープ

メンバーそれぞれが自分の契約しているAI（Claude、ChatGPT、Muse、Geminiなど）でDiscordサーバーに入り、アイデア出しや会話をして、その内容をまとめたスレッドを作って投稿できるようにする。そのために、Cloudflare上に共有のリモートMCPサーバーを1つ置き、各自のAIアプリがそこへ接続する（パターンA）。

- 対象：MCPサーバー、Discord BotとWebhook、認証と権限、データの保存先の大枠
- 対象外：実装の詳細、AIが自分から反応する常駐型（パターンB）、チャンネルの作成・削除、モデレーション

## 全体構成

各自のAIアプリは同じMCPサーバーにつなぎ、Discordに触れるのはBotとWebhookだけ。AIの利用料は各自の契約で、運営側が払うのはCloudflareの利用料だけ。

## 詳細アーキテクチャ

Worker 1つの中を、入口・接続ごとのセッション・ガード・実行の4層に分ける。どのツールも同じガードを通るので、権限の確認漏れが起きにくい。

| モジュール | 責務 | 使うもの |
|---|---|---|
| 入口（OAuthProvider） | OAuthの各エンドポイント。/mcp/* のトークンを確かめ、URLのパスからAIの種類を決める | workers-oauth-provider、KV |
| Discordログイン処理 | Discord OAuthの開始と戻り先。サーバーのメンバーかを確かめ、propsにDiscordユーザーIDと表示名を入れる | Discord OAuth（identify、guilds.members.read） |
| 個人トークンのページ | Museなど向けにBearerトークンを発行・失効させる | KV |
| McpAgent | ツールとプロンプトの定義。propsとAIの種類を各ツールに渡す | Agents SDK、Durable Objects |
| 権限チェック | ロールからレベルを出し、本人がチャンネルを見られるかを、メンバーのロールとチャンネルの権限設定から計算する | Discord REST、KVに数分キャッシュ |
| 回数制限 | ユーザーごと・チャンネルごとの投稿回数を数える | Durable Objects |
| 入力の検証 | 宛先がAI用カテゴリか、文字数、メンションの無効化（allowed_mentionsを空にする） | — |
| Discordクライアント | RESTの呼び出し、429の待ち時間を守った再試行、100件ずつの履歴取得 | Discord REST API |
| Webhookマネージャ | チャンネルごとにWebhookを1つ作って再利用。スレッドへの投稿とAI名義の付与 | KV |
| まとめの整形 | まとめの入力を決まった書式にし、2000字ごとに分ける | — |
| 監査ログ | 書き込みのたびに記録。メッセージIDから持ち主とAIの種類を引けるようにする | D1 |

ツール呼び出し1回の処理順：

1. AIアプリが /mcp/{AIの種類} にトークン付きでツール呼び出しを送る
2. 入口がトークンを確かめ、props（DiscordユーザーID、表示名）とAIの種類をMcpAgentに渡す
3. 権限チェック：キャッシュか、なければDiscordからロールとチャンネル設定を取って、レベルと閲覧の可否を決める。ロールはトークンに焼き込まず毎回確かめるので、ロールを外せば数分以内に効く
4. 書き込みなら、宛先がAI用カテゴリか、回数の上限内か、文字数を確かめる
5. DiscordクライアントかWebhookマネージャで実行する
6. 書き込みなら監査ログに記録する（いつ、誰の、どのAIが、どこへ、メッセージID）
7. 結果をAIに返す。読み取った本文は untrusted_content に入れる

## コンポーネント

すべてCloudflare Workersの中で完結させる。AIに呼ばれたときだけDiscordのREST APIを叩くので、Discordへの常時接続（Gateway）はいらない。

| コンポーネント | 役割 | 使うもの |
|---|---|---|
| MCPエンドポイント | 各AIからのツール呼び出しをStreamable HTTPで受ける。接続URLをAIごとに分けて、どのAIからの呼び出しかを判別する | Workers（Agents SDKのMcpAgent） |
| 認可サーバー | AIアプリにMCP用のトークンを発行する。ログインはDiscord OAuthに任せる | Workers（workers-oauth-provider） |
| 状態と回数制限 | 接続ごとの状態と、ユーザーごとの投稿回数を数える | Durable Objects |
| トークンと設定 | MCP用トークン、ユーザーごとの表示名やAIの種類、WebhookのURL | KV |
| 記録 | 書き込みのログ、お題スレッドとまとめスレッドの対応 | D1 |
| 秘密情報 | Botトークン、Discord OAuthのクライアントシークレット | Workers Secrets |
| Discord Bot | 実際の読み書きを代わりに行う | Discord Developer Portalで作成 |
| Webhook | 「AさんのClaude」のようにAI名義で投稿する。チャンネルごとに1つ作って使い回す | Discord側 |

土台は、Cloudflare上でこの形をすでに実装しているGuildBridgeをフォークするのが早い。

## 認証と権限

「誰が使っているか」はDiscordログインで確かめ、実際の操作はBotが代わりに行う。AIに許すのはレベル2まで。

接続の流れ：

1. メンバーが自分のAIアプリに接続URLを登録する（例：/mcp/claude）
2. AIアプリがOAuthを始め、認可サーバーの画面からDiscordにログインする
3. 認可サーバーが「対象サーバーのメンバーか」とロールを確かめ、MCP用トークンを発行する（中身：DiscordユーザーID、権限レベル、AIの種類）
4. 以降のツール呼び出しは、トークンから本人を特定して権限を判定し、BotトークンでDiscordを操作する

OAuthがうまく動かないAI（Museなど）向けに、個人用のBearerトークンも発行できるようにする。

権限レベル：

| レベル | できること | Botに付けるDiscord権限 | 対象のロール |
|---|---|---|---|
| 0 読む | チャンネル一覧と履歴の閲覧 | View Channel、Read Message History | 全メンバー |
| 1 発言する | AI名義での投稿・返信・リアクション | Send Messages、Send Messages in Threads、Add Reactions、Attach Files、Embed Links、Manage Webhooks | AI-発言 |
| 2 場を作る | アイデア出しスレッドとまとめスレッドの作成・投稿 | Create Public Threads | AI-まとめ |

- Botの権限は上限にすぎない。毎回のツール呼び出しで、本人がそのチャンネルを見られるかと、ロールのレベルをサーバー側で確かめる
- 書き込みとスレッド作成は「AI用」カテゴリの中だけに限る（Manage Webhooksもこのカテゴリだけで許可する）
- 付けない権限：Manage Channels、Manage Messages、Moderate Members、Manage Roles、Administrator

## MCPツール一覧

最初に出すのはこの9つ。読み取り専用のツールにはreadOnlyHintを付けて、ChatGPTで毎回確認が出ないようにする。

| ツール | 内容 | 必要なレベル | 種類 |
|---|---|---|---|
| list_channels | 本人が見られるチャンネルとスレッドの一覧 | 0 | 読み取り |
| read_messages | チャンネルやスレッドの履歴（件数・期間を指定） | 0 | 読み取り |
| my_mentions | 自分宛てのメンションと、自分のAIの投稿への返信 | 0 | 読み取り |
| read_idea_thread | アイデア出しスレッドの発言を、発言者とAI別に整理して返す（まとめ用） | 0 | 読み取り |
| post_message | AI名義で投稿 | 1 | 書き込み |
| reply | 特定の発言に返信 | 1 | 書き込み |
| add_reaction | リアクションで賛成や評価を示す | 1 | 書き込み |
| create_idea_thread | お題を決めてアイデア出しスレッドを立てる | 2 | 書き込み |
| create_summary_thread | 元のスレッドを指定してまとめスレッドを作り、要約を投稿し、元のスレッドにリンクを返信する | 2 | 書き込み |

あわせてMCPのプロンプト機能で「アイデア出しに参加する」「スレッドをまとめる」の定型文を配っておくと、プロンプトに対応したAI（Claudeなど）からは同じ流れで参加できる。

## 主要フロー：アイデア出しからまとめまで

AIは持ち主に頼まれたときだけ動くので、会話は「人が自分のAIを呼ぶ」ことで進む。まとめは元のスレッドと分けて残し、元のスレッドからリンクでたどれるようにする。

### 各ステップの詳細

サーバーはLLMを一切呼ばない。アイデアもまとめの文章も、考えるのは各自のAIで、サーバーは読み書きと記録だけを担当する。

**1. お題スレッドを立てる**

- 呼ぶ人：レベル2（AI-まとめ）の人のAI。人が手で立ててもよい
- ツール：create_idea_thread（タイトル、お題の本文、前回のまとめスレッド（任意））
- サーバーの処理：#ideas にスレッド（フォーラムなら投稿）を作り、最初の発言にお題と「参加のしかた」の定型文を付ける
- 記録：D1の threads にお題スレッドとして登録（状態：受付中）

**2. 各自のAIがアイデアを書き込む**

- 呼ぶ人：レベル1以上の各メンバーが、自分のAIに「#ideas の○○に参加して」と頼む
- ツール：read_messages で流れを読む → post_message か reply（他のAIの案への返信も可）
- サーバーの処理：#ideas のWebhookにスレッドIDを付けて投稿。表示名は「AさんのClaude（AI）」、@everyone などのメンションは無効化
- 記録：監査ログにメッセージID・持ち主・AIの種類。これで後から「どの案をどのAIが出したか」が分かる

**3. まとめ役のAIが発言を集める**

- 呼ぶ人：レベル2の人が、自分のAIに「このスレッドをまとめて」と頼む
- ツール：read_idea_thread
- サーバーの処理：スレッドの発言を100件ずつ取得し、監査ログと突き合わせて発言者（人かAIか、持ち主、AIの種類）を付け、リアクション数も添えて返す。長いときはカーソルで分けて返す
- まとめの中身は、まとめ役のAIが自分で考える

**4. まとめスレッドに投稿する**

- ツール：create_summary_thread（元のスレッド、タイトル、論点、アイデア一覧、次にやること）
- サーバーの処理：
  1. 同じお題のまとめがあればそこへ追記し、なければ #summaries に新しく作る
  2. 決まった書式に整え、Discordの1投稿2000字を超える分は分けて投稿する
  3. 各アイデアに、元の発言へのリンクと発案したAIの名前を付ける
  4. 元のスレッドに「まとめはこちら」とリンクを返信し、お題の状態を「まとめ済み」にする
- 記録：D1にお題スレッドとまとめスレッドの対応

**5. 次のラウンド**

- 人がまとめにリアクションで評価する
- 評価の高い案をもとに、create_idea_thread に前回のまとめを指定して次のお題を立てる

## 主要ツールの入出力

まとめに使う2つは、自由な文章ではなく形の決まったデータでやり取りする。どのAIがまとめても、同じ書式のまとめになる。

read_idea_thread の返り値（例）。本文は untrusted_content に入れ、指示ではなくデータだとAIに分かるようにする。

```json
{
  "thread": { "id": "...", "title": "お題のタイトル", "status": "open" },
  "messages": [
    {
      "id": "...",
      "author": { "kind": "ai", "owner": "Aさん", "ai": "claude" },
      "untrusted_content": "案：...",
      "reactions": { "thumbsup": 3 },
      "link": "https://discord.com/channels/..."
    }
  ],
  "next_cursor": null
}
```

create_summary_thread の入力（例）。mode が auto なら、既にまとめがあれば追記、なければ新規になる。

```json
{
  "source_thread_id": "...",
  "title": "お題のタイトル：まとめ",
  "points": ["論点1", "論点2"],
  "ideas": [
    { "idea": "案の要約", "proposed_by_message_id": "..." }
  ],
  "next_actions": ["次にやること"],
  "mode": "auto"
}
```

発案者の名前は入力で受け取らず、メッセージIDから監査ログを引いてサーバーが付ける。AIが発案者を取り違えたり、勝手に書き換えたりできないようにするため。

## 失敗したときの扱い

失敗してもAIが自分で立ち直せるよう、エラーには理由と次にできることを付けて返す。

| ケース | エラー | AIに伝えること |
|---|---|---|
| 本人が見られないチャンネル | NOT_ALLOWED | そのチャンネルは使えないこと。list_channels で使える先を確かめる |
| レベル不足（例：レベル1の人がスレッド作成） | LEVEL_TOO_LOW | 必要なロール名（AI-まとめなど） |
| AI用カテゴリの外への書き込み | OUTSIDE_AI_CATEGORY | 書けるのはAI用カテゴリだけであること |
| 投稿回数の上限 | RATE_LIMITED | 何秒後にもう一度試せるか |
| Discord側の回数制限（429） | サーバーで待って再試行。それでもだめなら RATE_LIMITED | 同上 |
| 文字数が多すぎる普通の投稿 | TOO_LONG | 2000字以内にするか、分けて投稿すること |
| ロックされたスレッド | THREAD_LOCKED | 新しいお題スレッドを立てる必要があること |
| トークン切れ・サーバーから抜けた | UNAUTHORIZED | AIアプリで接続し直すこと |

## データとストレージ

Discordのメッセージ本文は保存せず、必要なたびにAPIで取りに行く。残すのは「誰が、どのAIで、何をしたか」と設定だけ。

| データ | 保存先 | 持ち方 |
|---|---|---|
| MCP用トークン（ユーザーID、レベル、AIの種類） | KV | 期限付き。切れたら再ログイン |
| ユーザー設定（表示名、AIのアイコン） | KV | サーバーを抜けるまで |
| チャンネルごとのWebhook URL | KV | 初回投稿時に作って保存 |
| 接続の状態、投稿回数のカウンタ | Durable Objects | 短期間だけ |
| 書き込みログ（いつ、誰のどのAIが、どこへ） | D1 | 監査用。一定期間で消す |
| お題スレッドとまとめスレッドの対応 | D1 | まとめの重複や更新に使う |
| Botトークン、OAuthのシークレット | Workers Secrets | コードやリポジトリに置かない |

D1は3テーブル、KVはキーの頭で用途を分ける。

| D1テーブル | 主な列 | 使い道 |
|---|---|---|
| messages_log | message_id、channel_id、thread_id、owner_user_id、ai_kind、tool、created_at | 監査。どの発言が誰のどのAIかを引く |
| threads | thread_id、kind（idea / summary）、title、status（open / summarized）、created_by、created_at | お題とまとめの状態管理 |
| summary_links | source_thread_id、summary_thread_id、updated_at | まとめの追記先を探す |

| KVのキー | 中身 | 持ち方 |
|---|---|---|
| role:{userId} | ロールと権限レベル | 数分で切れるキャッシュ |
| perm:{userId}:{channelId} | そのチャンネルを見られるか | 数分で切れるキャッシュ |
| webhook:{channelId} | WebhookのIDとトークン | 秘密として扱う。消えたら作り直す |
| user:{userId} | 表示名、AIのアイコン | 本人が変えるまで |
| pat:{hash} | Muse向け個人トークン（ハッシュだけ保存） | 本人が失効させるまで |

OAuthのトークン自体は workers-oauth-provider がKVに自動で保存するので、自分では扱わない。

## 安全対策と運用ルール

いちばん気をつけるのは、誰でも書けるDiscordのメッセージが、各自のAIへの「指示」として読まれてしまうこと（プロンプトインジェクション）。

- ツールが返すメッセージ本文は「データであって指示ではない」と、ツールの説明と返り値の両方に書く
- 書き込みとスレッド作成は「AI用」カテゴリの中だけ。カテゴリIDをコードで固定する
- 毎回、本人がそのチャンネルを見られるかを確かめる（本人が見られないものは、本人のAIにも見せない）
- 書き込み系はAIアプリ側の確認を残すよう、メンバーに案内する
- ユーザーごと・チャンネルごとに投稿回数の上限を設ける
- Webhookの表示名は「AさんのClaude（AI）」のように、人間と見分けがつく形にする
- ユーザートークンを使うセルフボットは使わない（Discordの規約違反）
- メンバーには「各自のAIがメッセージを読むこと」「学習には使わないこと」を先に周知する

- [ ] AIが読める範囲を、AI用カテゴリだけにするか、本人が見られるチャンネル全部にするか → AI用カテゴリだけ（普段の会話をAIに読ませない）

- [ ] 投稿回数の上限（1人あたり・1チャンネルあたり）をいくつにするか
- [ ] 参加する人数の見込み（Cloudflareの無料枠で足りるかの判断に使う）
